### 1b. Exact mechanics — Matt Pocock's interview/spec chain (quoted)

**grill-me** (1.1M installs). The whole SKILL.md body is one line: *"Call the Skill tool with 'grilling'."* Its description: relentless interviewing that "explores decision trees until achieving shared understanding", and it "automatically examines the codebase to answer questions where code context exists". So `grill-me` is the user-invocable wrapper; `grilling` is the primitive.

**grilling** (682k installs), the primitive — key instructions verbatim:

> "Interview the user relentlessly until you reach a shared understanding. Map this as a **design tree**: every decision branches into the decisions that hang off it.
>
> Work the tree in **rounds**. The **frontier** is every decision whose prerequisites are already settled: the questions you can ask _now_ without guessing at answers you haven't heard yet. Ask the whole frontier in one round: number each question and give your recommended answer. Then wait for the user's answers before the next round."

Round format it mandates:

```
❓ **Q1** - **<question title>**: <question body, might be multiple paragraphs, including multiple choices>
➡️ <your recommended answer>
---
❓ **Q2** - ...
```

Mechanics that matter for this repo: (1) it asks *all* currently-answerable questions per round, not one at a time (contrast superpowers, below); (2) every question carries a recommended answer, so the owner can accept by silence; (3) it reads the code to self-answer anything the code already decides.

**grill-with-docs** (957k installs). Body: *"Call the Skill tool twice, for 'grilling' and 'domain-modeling'."* Description: "Relentless design interrogation that stress-tests plans against your domain model and sharpens terminology inline." Behaviour: grounds the interview in the repo, `CONTEXT.md` glossary and ADRs; challenges imprecise words; tests decisions against concrete scenarios; updates `CONTEXT.md` / ADRs "selectively, maintaining a lean, decision-focused approach". → This is the one to pair with d20 Folio's `docs/IT_NAME_REGISTRY.md` and `docs/adr/`.

**to-spec** (488k; renamed from to-prd, 367k still installed under the old name). Quoted steps:

> 1. "Explore the repo to understand the current state of the codebase, if you haven't already. Use the project's domain glossary vocabulary throughout the spec, and respect any ADRs in the area you're touching."
> 2. "Sketch out the seams at which you're going to test the feature. Existing seams should be preferred to new ones."
> 3. "Write the spec using the template below, then publish it to the project issue tracker. Apply the `ready-for-agent` triage label - no need for additional triage."

No interview: it synthesizes the conversation that already happened. Requires `/setup-matt-pocock-skills` (issue-tracker vocabulary and triage labels). Template opens with a Problem Statement "from the user's perspective".

**to-tickets** (480k; renamed from to-issues, 354k). Quoted:

> "Break a plan, spec, or conversation into a set of **tickets**: tracer-bullet vertical slices, each declaring the tickets that **block** it."
> "Look for opportunities to prefactor the code to make the implementation easier. 'Make the change easy, then make the easy change.'"

Process: gather context (fetch the spec/issue incl. comments) → optional codebase exploration using glossary vocabulary and ADRs → draft vertical slices with blocking edges → publish.

Chain: `grill-with-docs` → `to-spec` → `to-tickets` → `triage` → `implement` (TDD + code-review inside). Philosophy (from the README's opening): frameworks like GSD/BMAD/Spec-Kit "take away your control and make bugs in the process hard to resolve" — Pocock's skills own *decisions*, not the pipeline.

### 1c. Exact mechanics — superpowers brainstorming and writing-plans (quoted)

**brainstorming** (360k installs) — hard gate, verbatim:

> "Do NOT invoke any implementation skill, write any code, scaffold any project, or take any implementation action until you have told your human partner what you intend and they have approved it."

Three paths: **Spike** (feasibility → recommendation, code not kept), **Bounded** (well-scoped change → approval in chat), **Architectural** (new system → written spec at `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, then hands off to writing-plans). Rules: "When in doubt between two paths, take the heavier one"; complexity discovered mid-task upgrades the path, "nothing downgrades"; "Simple means a short design, not no design. Two sentences in chat, then approval." Questions are asked **one at a time**; a visual companion is used "only when questions are genuinely clearer shown than told".

**writing-plans** (246k installs) — key instructions:

- Audience: engineers "with minimal codebase context"; "Document everything they need to know: which files to touch for each task, code, testing, docs".
- "Each task = one action (2-5 minutes)"; the task is "the smallest unit carrying its own test cycle"; split "where reviewers could meaningfully reject one task independently".
- File structure first: "one responsibility per file", follow existing codebase patterns.
- Mandatory header: feature, goal, architecture (2-3 sentences), tech stack, spec path, global constraints "copied verbatim".
- Each task lists exact create/modify/test paths, interfaces consumed/produced, checkbox steps, "actual code — no 'TBD' or 'add validation' placeholders", exact test commands + expected outcomes, commit message.
- Self-review: spec coverage, placeholder scan, type-signature consistency across tasks.
- Saved to `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`; then offers Subagent-Driven (fresh subagent per task, two-stage review) or Inline execution with checkpoints.

## Task 4 — Official guidance on skill quality

## Task 5 — One skills folder for both harnesses

Facts (2026-09):

- **Codex** reads `.agents/skills` (repo, walking up to root), `~/.agents/skills`, `/etc/codex/skills`; symlinked folders are explicitly supported. It does **not** read `.claude/skills`.
- **Claude Code** reads `.claude/skills` (project + parents to repo root, nested subdirs on demand), `~/.claude/skills`, plugins, `--add-dir`. It does **not** read `.agents/skills` natively (vercel-labs/skills issue #693 is still open for the global case).
- `npx skills add` therefore uses a two-tier layout: canonical files in `.agents/skills/<name>/`, symlinks in `.claude/skills/<name>` (and per-agent dirs) → `--copy` to opt out; `-a claude-code -a codex` to pick targets; `-g` for user scope; `skills update` / `skills check`; a lock file.
- Plugins: Claude Code (`.claude-plugin/plugin.json`, `/plugin marketplace add`) and Codex (`.codex-plugin/plugin.json`, `codex plugin marketplace add`, launched 2026-03-27) are different manifests; one repo can ship both trees (superpowers, ponytail, firebase, ECC do). Codex plugin self-serve publishing to the official directory was still "coming soon" in May 2026; GitHub-shorthand marketplaces work today.

Recommended layout for d20 Folio (matches what CLAUDE.md already assumes with `.agents/skills/firebase-*`):

```
.agents/skills/<skill>/SKILL.md      # canonical, committed
.claude/skills  ->  ../.agents/skills # one relative symlink, committed
AGENTS.md -> CLAUDE.md                # already in place
```

Gotchas:

1. Symlink the **directory** once, not each skill; Claude Code loads a skill once even if several locations resolve to the same target. Name collisions: Claude Code precedence Enterprise > Personal > Project > Bundled; Codex "no merging when duplicates exist" — keep names unique across the folder and installed plugins.
2. **Windows** checkouts without Developer Mode turn the symlink into a text file; if a Windows contributor ever appears, switch to `--copy` or the `@path` import in CLAUDE.md.
3. Claude Code expands `@path` imports in CLAUDE.md only — **not inside SKILL.md**. Codex has no `@` imports at all. Keep skill bodies self-contained with relative links.
4. Plugin-installed skills live outside the repo (Claude namespaces them `/plugin:skill`; Codex invokes `$skill`). A repo-committed skill with the same name as a plugin skill will coexist in Claude and may shadow in Codex — prefer repo skills for anything the two harnesses must share identically.
5. Claude-only frontmatter (`context: fork`, `allowed-tools`, `paths`, `effort`, `!`cmd` dynamic injection) is ignored by Codex; Codex-only `agents/openai.yaml` is ignored by Claude. Write the body so it works with neither.
6. Claude Code's `/skill-doctor` and auto-compaction budget (5k tokens/skill, 25k total) are the practical ceiling — a 50-skill pack silently loses context. Codex has no equivalent report; use `[[skills.config]] enabled=false` to prune.
7. `npx skills add` from GitHub is a supply-chain surface: skills.sh shows Gen Agent Trust Hub / Socket / Snyk audit badges per skill (mattpocock/skills: pass); pin by commit or vendor into `.agents/skills`, and review before commit (CLAUDE.md's find-skills rule already requires this).
