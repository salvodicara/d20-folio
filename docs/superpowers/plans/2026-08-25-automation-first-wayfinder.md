# Automation-First Architecture Reset Wayfinder

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:writing-plans` to write a detailed child plan for every slice below, then use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to execute that child plan. This Wayfinder coordinates the program; it is not permission to start coding.

**Goal:** Replace the accumulated dual runtime with one deterministic command kernel that automates every knowable D&D consequence, asks the table only for external observations, and serves solo, shared play, onboarding, and every UI surface without duplicated rules or state.

**Architecture:** One locale-free `resolveCommand` kernel consumes typed rules, canonical material state, a semantic command, and external answers. Solo play executes it locally and writes one canonical character state document through Firestore offline persistence. Shared play sends the same command to an authenticated callable, which loads authoritative facts, runs the same bundled kernel, and transactionally writes changed aggregates plus a receipt. React renders semantic `ActionFlow` views and never owns rule math.

**Tech Stack:** React 19, strict TypeScript, Zustand, Firebase Auth/Firestore/Functions/App Check, Vitest, Playwright, pnpm at the repository root, standalone npm in `functions/`, and the existing content-pack seam.

**Spec:** `docs/plans/2026-08-24-automation-first-product-reset.md`

**Required companion:** `docs/superpowers/plans/2026-08-25-test-portfolio-reset.md` is a mandatory dependency for every implementation slice. It owns portfolio retention, deletion, and lane selection; this Wayfinder specifies only the behavioral proof each slice must provide.

## 3. Target Architecture

```text
typed SRD/private/homebrew RuleDefinition
                    │
                    ▼
canonical WorldState + SemanticCommand + ExternalAnswers
                    │
                    ▼
          resolveCommand(input, mode)
                    │
       ┌────────────┼──────────────┐
       ▼            ▼              ▼
NeedExternalInput  Rejected   Preview | CommitResult
                                  │
                       patches + events + receipt
                                  │
             ┌────────────────────┴───────────────────┐
             ▼                                        ▼
 local solo executor                         shared callable adapter
 one combat/state write                      one server transaction
             │                                        │
             └──────── semantic ActionFlow views ─────┘
```

### Kernel contract owned by Slice K1

The exact exported vocabulary is:

- `RuleDefinition` is versioned/provenanced rule data; `WorldState` is the minimum locale-free canonical fact set.
- `SemanticCommand` carries stable actor/subject/rule identity, choices, and expected revisions; `ExternalAnswers` contains only selected targets, table geometry, physical/hidden outcomes, or rulings.
- `ExternalInputRequest` is semantic and constrained; `ResolutionOutcome` is `NeedExternalInput | Rejected | Preview | CommitResult`.
- `CommitResult` carries patches/events/revisions/bounded undo receipt; `resolveCommand(input)` is the only production resolution entry point.

The child plan must freeze these as serializable strict-TypeScript interfaces in `src/types/command.ts`, `src/types/rule-definition.ts`, and `src/types/effect-instance.ts` before adapters are built.

### Boundary law

| Layer            | May own                                                                      | Must not own                                        |
| ---------------- | ---------------------------------------------------------------------------- | --------------------------------------------------- |
| Typed data       | rule facts, stable IDs, provenance, localized content references             | active runtime state, UI decisions                  |
| Command kernel   | legality, costs, target constraints, requests, patches, events, undo         | React, i18n, Firebase, clocks, RNG                  |
| State assemblers | canonical aggregate loading and revision projection                          | rule consequences                                   |
| Local executor   | preview/commit orchestration and one personal-state write                    | a second reducer or queue                           |
| Shared callable  | auth, App Check, membership, revision checks, transaction, receipt retention | duplicated gameplay math or client-supplied patches |
| Presenters       | semantic labels, grouping, tone, formatting, ActionFlow step model           | legality or mutation                                |
| React UI         | display, focus, input capture, confirmation, screenshot-approved motion      | parsing prose or deriving mechanics                 |
| Firestore Rules  | identity, membership, authority mode, field shape, size limits               | damage, spell, effect, turn, or resource validation |

### Import direction

`src/data + src/types` → `src/lib/command` and existing pure rules → `src/lib/views` and executors → `src/features + src/components + src/app`; the Functions gameplay adapter bundles the same `src/lib/command` source.

`src/lib/command/**` must be guarded from imports of React, Firebase, Zustand, `src/i18n/**`, `src/features/**`, and `src/components/**`.

Functions must not contain a copied kernel. `scripts/build-functions.ts` will bundle the root kernel source into the Functions artifact with `esbuild`, while Firebase packages remain external and the existing private content-pack alias behavior is preserved.

### Canonical Firestore ownership

```text
users/{uid}/characters/{characterId}
  build + custom content + metadata + sharing/attachment + buildRevision + derived cache
  combat/state
    one versioned CharacterMaterialState; all personal live facts
  public/sheet
    derived share projection; never another mutation authority

campaigns/{campaignId}
  identity + settings + treasury + activeEncounterId + memberUids query index
  members/{uid}
    canonical membership, role, attached characterRef, participation state
  encounters/{encounterId}
    one bounded SharedMaterialState: NPC facts, PC refs, initiative, turn, clock, shared effects
    receipts/{commandId}
      immutable bounded shared command receipt
  sessionProposals/{proposalId}
    bounded windows + draft agenda + encounterRef + lifecycle/revision
    availability/{uid}
      one member's availability
  sessions/{sessionId}
    chosen slot/timezone + final agenda + encounterRef + lifecycle/revision
    rsvps/{uid}
      one member's RSVP
  notes/{noteId}
    one authored campaign/session note with optional sessionRef
  chronicle/{entryId}
    one authored historical entry with optional sessionRef; never a copied planner timeline
  homebrewPins/{pinId}
    exact immutable account definition version + fingerprint + provenance

users/{uid}/homebrew/{definitionId}
  account-library identity, kind, presentation metadata, draft pointer, published pointers
  versions/{versionId}
    typed definition + lifecycle + provenance + fingerprint; published versions immutable
```

There is no persisted pending-command collection, no PC build/HP/slot/inventory/resource mirror inside an encounter, and no inline encounter, `memberEffects`, `effectOps`, `world`, character snapshot, or shared-note mirror on the campaign parent.

### Access matrix

| Path                        | Read                                                              | Direct client write                | Server write                                  |
| --------------------------- | ----------------------------------------------------------------- | ---------------------------------- | --------------------------------------------- |
| Character parent            | owner; authorized share projection consumers only                 | owner for build/custom/meta fields | migrations and derived projection maintenance |
| Personal `combat/state`     | owner; attached campaign participants according to sharing policy | owner only in solo authority mode  | shared command and migrations                 |
| `public/sheet`              | policy-authorized viewers                                         | none after cutover                 | derived projection only                       |
| Campaign parent/member docs | campaign members; invite/join through callable policy             | none for membership or query index | campaign callables only                       |
| Encounter                   | campaign members                                                  | none                               | shared command and encounter callables only   |
| Receipt                     | authorized encounter participants                                 | none                               | immutable create plus bounded retention only  |
| Homebrew account library    | owner; pinned versions via authorized server projection           | owner draft only                   | validated publish/archive and campaign pin    |
| Planner/chronicle records   | campaign members                                                  | own availability/RSVP only         | proposal/session/agenda/note/chronicle policy |

Rules may inspect authentication, parent ownership, membership existence, attachment authority, document keys/types/sizes, and immutable IDs.

Rules may not inspect a spell formula, calculate damage, validate an effect transition, or recreate command proofs.

Calendar export is a pure, explicit projection of scheduled sessions; it owns no document, background sync, polling loop, or duplicate campaign timeline.

### Solo and shared command flow

**Solo:** assemble `WorldState`, run `resolveCommand`, apply through one local executor, and write only `combat/state`; Firestore supplies the offline queue while `fromCache`/`hasPendingWrites` expose durability.

**Shared:** preview locally, then send command/answers—not patches—to `executeSharedCommand`; the server verifies Auth/App Check/role/participation/build and aggregate revisions/identity, loads trusted rules/facts, runs the same kernel, and transactionally writes changed documents plus an immutable idempotent receipt. Offline retains only an in-memory draft and must reconnect, reload, and re-preview before commit.

Before it lands, the child plan names parity evidence, owner-gated migration, and the exact next deletion commit; after verified migration, that commit removes the bridge and representation tests.

## 20. Review and Verification Gates

Every slice must pass these gates in order:

1. **Plan gate:** detailed child plan reviewed for scope, ownership, deletion, migration, tests, and owner pauses.
2. **Specification gate:** independent reviewer checks behavior against the reset spec and product constitution.
3. **Boundary gate:** import graph and search prove no new reverse dependency or duplicate rule owner.
4. **Correctness gate:** focused retained tests fail before behavior code where applicable and pass after it.
5. **Security gate:** required for auth, Functions, Rules, hostile input, shared state, or cross-user access.
6. **Migration gate:** fixture snapshot → dry-run → idempotent apply test → verify; live apply waits for exact owner permission.
7. **Visual gate:** any visible change requires browser inspection and owner-approved actual screenshots before integration.
8. **Simplicity gate:** `ponytail-review` identifies scaffolding, compatibility code, and speculative abstractions to delete.
9. **Integration gate:** rebase on fresh `origin/main`, run authoritative gates, preserve unrelated changes, and integrate through the repository runbook.
10. **Deployment gate:** stop after integration; ask for explicit permission for the exact deploy and migration change.

T0 supplies focused commands; applicable slices still run Functions/browser builds, `pnpm test:rules`, `just ci-srd-only`, and `just ci`. No worker uses `--no-verify` or treats a focused green subset as permission to skip the composed gate.

## 22. Program Completion Criteria
